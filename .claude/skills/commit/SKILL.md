# commit: 변경사항 분석 후 컨벤션 커밋

작업 트리의 변경사항을 분석해 논리적 단위로 나누고, 한국어 커밋 메시지를 작성해 **승인 절차 없이 바로** 커밋한다. 커밋 후에는 결과를 요약해 알린다.

## 워크플로우

### Step 0: 사전 확인

- 저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)가 있으면 읽고, 커밋 관련 지침이 있으면 이 스킬보다 우선한다.
- `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다. 아니면 커밋할 수 없다고 알리고 `git init`을 할지 사용자에게 묻는다. 묻기 전에 초기화하지 않는다.
- 기본 브랜치(`main`/`master`)에 있으면 먼저 사용자에게 알리고 새 브랜치를 만들지 확인한다.

### Step 1: 변경사항 분석

다음을 실행해 변경 전체를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 참고
```

- untracked 파일은 이름과 내용을 확인한다.
- diff가 크면 파일별로 나눠 읽는다. 파일 이름만 보고 판단하지 않는다.
- 변경이 전혀 없으면 "커밋할 변경사항이 없습니다"라고 알리고 종료한다.
- `.env`, 키·토큰·비밀번호가 포함된 파일, `node_modules/`, 빌드 산출물(`dist/` 등)은 커밋 대상에서 제외하고 사용자에게 알린다. 이미 staged라면 `git restore --staged`로 내리기 전에 사용자에게 확인한다.

### Step 2: 논리적 단위로 분류

하나의 커밋은 하나의 목적만 담는다.

- 서로 다른 목적(기능 추가 + 버그 수정 + 설정 변경)은 별도 커밋으로 나눈다.
- 같은 목적의 코드, 테스트, 스타일 변경은 한 커밋으로 묶는다.
- 한 파일에 목적이 섞여 있으면 `git add -p` 대신 사용자에게 분리 방식을 제안한다. 대화형 플래그는 이 환경에서 지원되지 않는다.
- 커밋 순서는 의존성 순으로 정한다. 예: 타입/유틸 → 기능 → UI.

### Step 3: 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<선택: 무엇을 왜 바꿨는지 본문>
```

| type | 용도 |
| --- | --- |
| `feat` | 사용자에게 보이는 기능·UI 추가/개선 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 설정, 의존성, 빌드, 문서 등 코드 외 작업 |

규칙:

- 요약은 한 줄, 50자 안팎, 마침표 없이 쓴다. 명령형보다 "~추가", "~수정", "~개선"처럼 명사형으로 끝낸다.
- "무엇을 했는가"보다 "무엇이 달라지는가"가 드러나게 쓴다. 예: `feat: 메뉴바와 창 UI 중심의 레트로 테마 적용`
- 본문은 요약만으로 이유가 설명되지 않을 때만 쓴다. 한 줄이 72자를 넘기지 않게 줄바꿈한다.
- 마지막에 빈 줄을 두고 시스템 지침에 지정된 attribution 줄(`Co-Authored-By: ...`)을 붙인다. 지정된 것이 없으면 붙이지 않는다.

### Step 4: 커밋 계획 안내 (승인 불필요)

Step 2~3에서 정한 계획을 한 번 출력한 뒤 곧바로 Step 5로 진행한다. 사용자의 승인을 기다리지 않는다.

```
커밋 계획 (N개)
1. feat: ...
   - src/App.tsx
   - src/App.css
2. chore: ...
   - package.json
```

- 사용자가 이미 메시지, 분리/병합, 제외할 파일을 지정했다면 그대로 따른다.
- 이 스킬이 하는 일은 이번 요청의 커밋까지다. `git push`는 별도로 요청받았을 때만 한다.

### Step 5: 커밋 실행

계획한 단위마다 순서대로 실행한다.

```bash
git add <파일...>          # 파일을 명시한다. git add -A / . 는 쓰지 않는다
git commit -m "$(cat <<'EOF'
<type>: <요약>

<본문>

Co-Authored-By: ...
EOF
)"
```

- 훅이 실패하면 `--no-verify`로 우회하지 않는다. 원인을 고치고 새 커밋으로 다시 시도한다.
- 이미 만든 커밋을 `--amend`하지 않는다. 사용자가 요청한 경우만 예외다.
- 모든 커밋 후 `git log --oneline -N`과 `git status --short`로 결과를 확인하고 요약해 알린다.

## 하지 않는 것

- `push`, `reset --hard`, `--force` 등 되돌리기 어려운 작업 (커밋 자체는 승인 없이 진행하지만 이 작업들은 별도 요청이 있어야 한다)
- 비밀 정보나 산출물 커밋
- 영문 메시지 작성. 사용자가 요청하지 않는 한 한국어로 쓴다. type 접두사만 영문이다.
