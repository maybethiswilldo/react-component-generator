# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"로 처리하지 않는다.

## 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선한다.**
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 다루지 않는 부분에만 적용한다.

## 1. 적용 기준

### TDD를 반드시 적용하는 대상

- **비즈니스 로직**
- **API** (엔드포인트, 요청/응답 처리, 외부 API 호출 래퍼)
- **유틸 함수** (순수 함수, 변환/정규화/파싱 로직)
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)

### TDD가 불필요한 대상

- **타입 정의** (`interface`, `type`)
- **설정 파일** (tsconfig, vite/eslint 설정, package.json 등)
- **순수 UI** (로직 없이 마크업·스타일만 있는 컴포넌트)
- **SQL** (스키마, 마이그레이션)

판단이 애매하면 **적용 대상으로 간주한다.** 조건문, 상태, 분기, 변환이 하나라도 있으면 순수 UI가 아니다.

## 2. RED - GREEN - REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에서 여러 동작을 검증하지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류, 설정 오류로 인한 실패는 RED가 아니다. 먼저 고치고 다시 실행한다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트를 고친다.

### GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI:** 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 않는다.
- 실행해서 **신규 테스트와 기존 테스트 모두 통과**하는지 확인한다. 하나라도 실패하면 GREEN이 아니다.

### REFACTOR: 정리

- **중복 제거, 이름 개선, 헬퍼 추출**만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 모든 동작이 끝날 때까지 사이클을 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 포함한다. 보고 있는 코드에 맞춘 테스트는 TDD가 아니다.
- 삭제는 협상 대상이 아니다.

## 4. 변명 차단표

| 변명 | 반론 |
| --- | --- |
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트도 30초면 쓴다. 단순한 코드가 가장 자주 깨지고, 테스트가 없으면 깨진 줄도 모른다. |
| "나중에 추가하겠다" | 나중에 쓰는 테스트는 이미 구현된 코드에 맞춰진다. 처음부터 통과하므로 아무것도 증명하지 못한다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅과 회귀 수정으로 더 많은 시간을 쓴다. 시간이 없을수록 TDD가 빠르다. |
| "삭제하면 낭비다" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 것이 진짜 낭비다. 다시 쓰는 비용은 작고, 잘못된 코드를 안고 가는 비용은 크다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 테스트도 가볍게 쓰면 된다. 규칙 적용 여부를 정하는 기준은 용도가 아니라 대상이다. |
